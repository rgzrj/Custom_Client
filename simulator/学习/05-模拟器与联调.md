# 第 5 阶段：用模拟器理解数据、视频和界面

你做视觉算法，可以把这里理解为“可控制的测试数据源”。客户端相当于消费图像与状态的下游程序。
本阶段不用先学网页前端，也不修改正式通信。

## 第一步：看清两个窗口

- 客户端项目的 `run-terminal.cmd`：启动 Qt 客户端，观察 HUD。
- 本项目的 `run-simulator.cmd`：启动 Python 控制台，制造测试数据。

数据经过本机网络再进入客户端，模拟器不直接改 QML。代码入口是
[`control_console.py`](../simulator/control_console.py) → [`console_session.py`](../simulator/console_session.py)
→ [`sim_state.py`](../simulator/sim_state.py) → [`sim_referee_receiver.cpp`](../../client/src/sim/sim_referee_receiver.cpp)。

## 第二步：追踪血量

控制台选蓝方、英雄，在“双方机器人”把蓝方英雄血量改成 200，点击应用。
检查左下角本车血条。切换本车到步兵3后，英雄变回顶部队友，血量仍应为 200。

看 `state_packet()`：本车血量取自 `robots[team][self_index]`，队伍栏也取同一组 `robots`，
所以不会出现一个地方阵亡、另一个地方满血。UI 只是编辑状态，没有第二份比赛数据。

验收：红/蓝切换不把两队的数据交换；本车切换不凭空回血；护盾不能超过上限。

## 第三步：区分视频文件、探针和真实视频包

本地 MP4 是播放器回放，与模拟器发包无关。
`probe` 是可数包的假视频，不能解码；`ts` 才是 MPEG-TS/H.264 图像。
客户端用 `-SimUdpVideo` 后，关闭 TS 发包才会真正断流。

验收：视频断流时数据仍更新；裁判数据过期时视频仍播放；恢复图传后不重启客户端也能继续出帧。
H.265 未验证；测试容器不是官方 UDP 分包。

## 第四步：制造网络故障

先只改一个参数，例如丢包 5%；再单独测延迟 100 ms、抖动、乱序。
每次记录客户端告警、是否冻结、恢复所需时间。不要把控制台“设置延迟 100 ms”当成实测总延迟。
损坏码流可能让解码器等下一个关键帧恢复，这比“开关视频在线标志”更接近真实问题。

## 第五步：把问题保存下来

场景 JSON 保存“怎么制造问题”；`.rm27-replay` 保存“实际发了哪些字节、何时发送”。
两者不同：重新运行场景可能受机器调度影响，而包回放保留一次运行的发送顺序和静默间隔。

练习：填入“独立断流恢复”，开始录制，10 秒后停止，再回放一次，检查 3–5 秒数据过期、7–9 秒视频断流。
若不用 `ts`，这一练习只能验证探针收包，不能证明解码器恢复。

测试入口（先切到 simulator 项目目录，不是其内部 Python 包目录）：

```powershell
D:\YOLOV8\python.exe -m unittest discover -s simulator -p "test_*.py"
```

完整操作、端口与文件限制见 [`模拟器说明`](../README.md)。所有字段均为项目决策，不是官方赛事协议。

## 第六步：独立回归与交付

网络单测现在每例自动申请独立端口，不用停止默认端口正在工作的模拟会话；排空接收队列有总超时，异常持续发送会明确失败，不一直等。应用默认端口保持不变，联调时同一默认端口仍只用一组会话。

只检查环境用 `.\run-simulator.cmd --check`；双方契约与 18 个样例见 [模拟接口-v1](../contracts/模拟接口-v1.md)。先分别跑两端测试，再运行 `scripts/check-contract.ps1 -ReferenceProject "客户端项目路径"`，防止字段只改一边。

分享给不装 Python 的同学时，用 README 中的独立便携模拟器包；解压完整目录后启动，不单发 exe。先做包哈希与隔离环境自检，再让另一台干净电脑实际验收。两个项目各自产出 ZIP，各写自己的 Edit.md，本机日志不上传、不进发布包。
