# 从“能收到包”到“能可靠显示”：网络通信与本机联调

适合对象：有 C++、Python 或计算机视觉经验，但不熟悉网络通信的开发者。本文围绕当前 Qt/QML 客户端展开，不要求先学习网页后端。

更新日期：2026-10-01。建议分三次学习，每次约 30 分钟。本文为原创教学整理，保留少量中英文原文链接，不复制外部文章全文。所有示例端口、主题、JSON 字段和超时阈值都是项目模拟约定，不是官方 RM2027 通信协议。

## 1. 先看懂一条链路，不要先背整个网络体系

你熟悉的 CV 程序可能是“摄像头 → 图像 → 算法 → 显示”。网络程序可以先理解成“发送者 → 传输 → 接收者 → 解析与校验 → 状态 → 显示”。

当前客户端的模拟裁判数据有两条入口，最后进入同一个解析器：

```text
模拟发送者 ── UDP 数据报 ─────────────────────┐
                                            ├→ JSON 校验与序号过滤 → 领域数据
本机模拟 broker ── TCP 上的 MQTT → 消息载荷 ──┘                       │
                                                                    ↓
                                                Controller → 属性通知 → QML HUD
```

两条入口不是两个独立的赛事状态源。它们共享裁判载荷的序号过滤，不要同时给同一个客户端灌入两套互不相关的序号流。

视频是另一条链路：收到数据、组装合法视频流、解码出帧、显示到屏幕不是同一件事。裁判数据正常时视频仍可能断流，视频正常时裁判数据也可能过期。

验收目标：你能分别回答“发给谁、用什么传、内容是什么、怎样判断有效、谁更新界面”。

## 2. 第一组术语：地址、端口与进程

| 术语 | 直白理解 | 本项目例子或注意点 |
| --- | --- | --- |
| IP 地址 / IP Address | 网络中定位主机或接口的地址 | `127.0.0.1` 是本机 IPv4 环回地址 |
| 端口 / Port | 配合地址与传输协议选择通信入口 | `UDP 39001` 与 `TCP 39001` 不是同一个入口 |
| 端点 / Endpoint | 通常指地址与端口的组合，还需明确协议 | 只说“39004”不如说“TCP，127.0.0.1:39004”准确 |
| 套接字 / Socket | 程序与操作系统交换网络数据的接口 | Qt 用 `QUdpSocket` / `QTcpSocket` |
| 绑定 / Bind | 给本地套接字指定接收地址与端口 | 接收者绑定环回地址和裁判 UDP 端口 |
| 监听 / Listen | TCP 服务端等待新连接 | MQTT broker 监听，客户端主动连接 |
| 环回 / Loopback | 同一台电脑内部的网络通信 | 不需要改网卡静态 IP，也不能用它连接另一台电脑 |
| 载荷 / Payload | 协议包里实际要传递的内容 | 当前 MQTT 消息的载荷是项目 JSON |
| 序列化 / Serialization | 把结构化数据编码成字节 | JSON 与 Protobuf 是不同的编码方案 |
| 新鲜度 / Freshness | 最近一次有效数据距现在多久 | 能连上不代表数据一直有效或新鲜 |

`0.0.0.0` 在 IPv4 服务绑定中通常表示所有本地接口，不是让发送者照填的目标主机地址。把环回绑定改成它会扩大网络暴露范围，不能为了“试试看”随意改。

本项目当前只允许本机模拟连接。将地址换成另一台电脑的 IP，并不能自动获得跨机能力：还涉及绑定范围、来源校验、路由、防火墙以及项目安全边界。

## 3. 第二组术语：UDP、TCP、MQTT、JSON、Protobuf不是同一层

| 名称 | 主要解决什么 | 不负责保证什么 |
| --- | --- | --- |
| UDP | 发送有边界的数据报 | 不保证送达、顺序或不重复 |
| TCP | 连接内可靠、有序的字节流 | 不替应用定义消息边界；不保证对端业务已经处理 |
| MQTT | 客户端经 broker 按主题发布与订阅消息 | 不决定载荷业务字段，也不直接证明机器人执行了动作 |
| JSON | 用可读文本表示数据结构 | 不是传输协议，不负责重连或确认 |
| Protobuf | 按消息定义编码、解析结构化数据 | 不是网络连接，也不自动提供认证、加密或完整业务校验 |

在常见 MQTT/TCP 链路中，你可以这样分层理解：TCP 搬运字节，MQTT 定义消息与主题，JSON 或 Protobuf 定义载荷内容。因此“MQTT 和 Protobuf 二选一”是混淆了层次。

当前项目是 MQTT 3.1.1 + JSON 的本机模拟路径，没有正式 Protobuf 接入。未来必须以官方 `.proto` 与通信文件为依据，不能把模拟 JSON 转成一个自拟 `.proto` 后称为官方协议。

### UDP：一条数据报有边界，但不能假设它一定到达

当前模拟裁判接口规定一条 UDP 数据报装一个 JSON 对象。接收端仍须检查报文长度、来源、版本、类型和范围；重复或乱序载荷也不能直接更新状态。

看 [Qt 官方中文：QUdpSocket](https://doc.qt.io/qt-6/zh/qudpsocket.html) 的“详细说明”和 `receiveDatagram`。注意读取缓冲不够时会截断数据，超大的网络报文也可能涉及分片。不要套用“UDP 永远比 TCP 快”这样的结论，延迟还取决于队列、处理与具体传输设计。

### TCP：收到一次数据，不等于收到一条完整消息

假设对端连续发送消息 A、B。接收方的一次读取可能只有 A 的前半段，也可能包含完整 A 和部分 B。这不是 TCP 把业务内容弄错，而是 TCP 本来就提供字节流，不保留应用消息边界。

应用需要按自己的协议切出完整消息，常见方法有长度前缀或分隔符。本项目 MQTT 接收器按 MQTT 的包头与 Remaining Length 解析，先积累到 `pending_`，等完整包到齐后再处理，并限制缓冲大小。

阅读 [Qt 官方中文：QTcpSocket](https://doc.qt.io/qt-6/zh/qtcpsocket.html)。回代码看 `readPackets()`，理解“收到字节”和“解析出消息”的区别。不要把 `readAll()` 的结果直接当作一个完整 JSON，也不要给 MQTT 随意加换行分隔。

### MQTT：连上、订阅成功、收到消息是三个步骤

先掌握四个词：broker 是转发消息的服务，publisher 发布消息，subscriber 订阅消息，topic 是主题名称。订阅主题本身不等于发布控制指令。

QoS 是消息交付等级：0 尽力交付、至多一次；1 至少一次，可能重复；2 在相应 MQTT 协议交付范围内恰好一次。**QoS 2 不能代替机器人业务动作的确认与去重**，也不能笼统理解为任何故障下都不会丢失。

Retained message 是 broker 为主题保留的最近消息；keepalive 用于连接活性检查，它们都不等同于裁判数据的新鲜度。看 [EMQ 官方中文：MQTT 协议快速入门](https://www.emqx.com/zh/blog/the-easiest-guide-to-getting-started-with-mqtt)，先读发布/订阅、主题和 QoS，暂时不用部署公网服务。

本项目只读模拟接收器只实现测试需要的 MQTT 子集，不是通用生产客户端；目前使用 clean session、没有 keepalive，重连后重新订阅。本机模拟 broker 不缓存旧裁判载荷，不提供真实上行控制。不能把这些设定照搬到正式通信。

### Protobuf：先理解 schema，不急着编写官方字段

`.proto` 描述消息结构，生成工具产生 C++、Python 等语言的代码，发送与接收双方再按同一份定义编码、解析。字段编号、兼容性和版本都需要管理；能解析不代表字段在业务上合法。

阅读 [Protocol Buffers 官方概述](https://protobuf.dev/overview/) 即可，先理解消息定义与生成代码。正式字段仍须等官方资料；本专题不安装生成工具，也不新增正式协议骨架。

## 4. 对照当前项目：四个端口分别做什么

以下来自本项目[模拟接口契约](../contracts/模拟接口-v1.md)，不是赛事网络配置。启动面板可以改变部分端口；排查时以实际配置为准，不只看默认值。

| 默认本机端点 | 内容 | 什么时候才算有效 |
| --- | --- | --- |
| UDP `127.0.0.1:39001` | 每包一个 UTF-8 JSON，最多 4096 字节 | 载荷通过字段和序号校验 |
| TCP `127.0.0.1:39004` | MQTT 3.1.1，QoS 0，主题 `rm27/sim/v1/referee`，同一 JSON 载荷 | 订阅成功且收到通过校验的新载荷 |
| UDP `127.0.0.1:39002` | 视频探针测试字节 | 只能说明测试包到达，不能证明能解码 |
| UDP `127.0.0.1:39003` | 本机 MPEG-TS 视频，每报文最多 7 个 188 字节 TS 包 | 视频后端产生有效解码帧；不是官方分包接收器 |

## 5. 为什么“连接正常”不等于“数据可用”

可以按五层依次判断，不要一上来就重装依赖：

| 层次 | 你要确认的问题 |
| --- | --- |
| 环境 | 进程是否运行，目标地址、协议、端口是否一致？ |
| 传输 | UDP 数据报是否到达，TCP 是否建立连接？ |
| 消息 | MQTT 是否订阅成功，包是否完整，主题是否正确？ |
| 数据 | JSON 是否合法，版本、类型、范围和序号是否被接受？ |
| 显示与权限 | 状态是否通知 QML，数据是否新鲜，当前模式是否允许操作？ |

当前项目收到有效裁判载荷后，按本机接收时刻刷新 600 ms 过期定时器；重复或乱序序号不刷新。过期后重置序号流，清空 HUD 与事件；新会话可以重新从低序号开始。该阈值是项目决策，不是官方时限。

数据更新只能说明模拟展示链路有效，不能解除模拟/回放模式禁止真实控制的边界。重连时也不能把断线期间积压的旧操作补发出去。

时间戳要分清：发送者的 Unix 时间是记录信息，本机单调时间用于衡量接收后经过多久。两台电脑时钟未校准时，简单相减不能证明单向链路延迟；本机模拟 `latency_ms` 和 `packet_loss_pct` 也不是实测指标。

## 6. 网络环境怎么查：先做只读检查

### 本机联调不需要先改网卡

使用 `127.0.0.1` 时，不需要设置赛事静态 IP、网关或 DNS。DNS 用于名称解析，填写数字 IP 的这一步不需要 DNS 查询。

以后若要连真实裁判网络，需要确认官方地址、子网、物理连接、路由、端口、认证和协议版本；现阶段不猜这些值，不关闭防火墙、不批量放开端口、不改系统 PATH。

### 在 PowerShell 中检查监听与绑定

这些命令只读本机状态；没有输出只说明没有匹配条目，不证明通信一定正常或异常。端口改过时，把下面数字换成当前配置。

```powershell
Get-NetUDPEndpoint | Where-Object { $_.LocalPort -in 39001,39002,39003 } |
    Select-Object LocalAddress,LocalPort,OwningProcess

Get-NetTCPConnection | Where-Object {
    $_.LocalPort -eq 39004 -or $_.RemotePort -eq 39004
} | Select-Object LocalAddress,LocalPort,RemoteAddress,RemotePort,State,OwningProcess
```

UDP 没有 TCP 那种 `Established` 连接状态。`OwningProcess` 是占用者 PID；确认是否是自己的客户端或模拟器，不能见到占用就关闭未知进程。

也可使用项目已有自检，在 PowerShell 中运行：

```powershell
Set-Location -LiteralPath 'D:\vs\vscode\c++\huge mas\Custom_Client\client'
.\scripts\check-environment.ps1
```

它先检查本机固定工具链，再查看默认端口占用，不改网卡、不连裁判系统。客户端或模拟器已经运行时，出现自己的端口占用提示可能完全正常。

`ping` 成功不证明应用端口或载荷正确；失败也不必然说明业务不可达，因为 ICMP 可能被限制。[Microsoft：Test-NetConnection](https://learn.microsoft.com/zh-cn/powershell/module/nettcpip/test-netconnection?view=windowsserver2025-ps) 的 `-Port` 检查是 TCP，不是 UDP。主动 TCP 测试会建立连接，可能影响单观察者测试 broker；本专题不执行这类测试，也不扫描未知地址。

### 两端契约一致，不代表所有测试都通过

需要比较客户端与相邻模拟器的契约时，可在客户端目录运行：

```powershell
.\scripts\check-contract.ps1 -ReferenceProject 'D:\vs\vscode\c++\huge mas\Custom_Client\simulator'
```

它只比较双方契约文档与固定样例的 SHA-256，不覆盖文件，也不能代替各自的解析和生成测试。为什么要保存固定样例，可看 [sim-v1-fixtures.json](../contracts/sim-v1-fixtures.json)：它帮助两种语言对同一输入作出一致的接受/拒绝判断。

## 7. 与 AI 讨论通信：不要只说“帮我接上”

可以用下面的短说明，让 AI 先定位问题而不是随意换网络配置：

```text
【范围】仅本机模拟通信，不连接官方裁判网络，不下发真实控制。
【链路】发送者 ______；接收者 ______；UDP/TCP/MQTT ______。
【端点与格式】实际地址、端口、主题、载荷版本分别是 ______。
【现象】最近一次正常行为 ______；现在 ______；错误原文 ______。
【依据】提供契约、脱敏样例和日志；不要猜官方字段。
【要求】先判断问题在环境、传输、消息、数据还是显示层。
【验证】区分已确认与猜测；不改网卡，不关闭未知进程。
```

例如：“本机 MQTT 已连接，但血量没有更新”仍然不够。应补充是否收到 SUBACK、消息主题、载荷 channel、sequence 是否递增、解析器是否接受、数据是否已经过期。日志和样例不要包含密码、令牌或个人隐私。

## 8. 三次学习练习

### 第一次：说清链路，不改代码

读 Qt UDP/TCP 的指定部分，画出裁判 UDP 和 MQTT 两条入口。回答：MQTT 主题在哪一层？JSON 在哪一层？为什么视频探针收到包不能证明出帧？

通过标准：能准确说出四个默认端口的用途，并区分 TCP 流与 UDP 数据报。

### 第二次：用已有模拟器观察数据新鲜度

使用你已经运行过的本机模拟器与客户端，不打开演示模式来替代通信检查。先只选择一条裁判发送路径，确认客户端与模拟器端口一致；MQTT 路径还须在客户端启用本机订阅。

改变本车血量，观察 HUD；然后只停止裁判数据发送，观察过期清空，再恢复发送。若同时有可解码视频，观察它是否独立继续运行。具体模拟器操作见相邻项目的[第 5 阶段：模拟器与联调](../../simulator/学习/05-模拟器与联调.md)。

通过标准：能区分“发包停止”“载荷被拒绝”“界面未通知”“演示数据”，并确认恢复后控制仍锁定。600 ms 是定时器设定，界面可见变化还受事件调度影响，不要求肉眼计时精确到毫秒。

### 第三次：检查异常，不扩展正式协议

先读固定样例与接收器过滤代码，不手工向真实网络发包。列出这些情况下预期行为：错误版本、缺字段、类型错误、超长包、重复序号、乱序、断线重连、两端契约漂移。

通过标准：知道在哪一层拒绝输入、怎样避免旧数据更新界面，以及哪些场景需要单测。新增字段或调整协议时，需要双方同步文档、样例与测试；本次学习不实施这些修改。
