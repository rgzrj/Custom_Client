# 从“好看一点”到设计说明：前端设计组织与 AI 协作

适合对象：有计算机视觉基础、刚开始接触界面设计的开发者。本文中的“前端”主要指当前项目的 Qt/QML 桌面界面，不要求先学习网页框架。

更新日期：2026-10-01。建议分三次阅读，每次约 20～30 分钟。本文是原创学习整理，不是外部文章的全文翻译；参考资料保留原文链接，项目示例和验收建议不属于官方赛事规则。

## 1. 你要培养的不是“会说高级感”，而是设计组织能力

设计组织能力可以拆成三件事：

1. **安排信息**：操作手当前在做什么？必须看到什么？哪些内容可以暂时收起？
2. **表达要求**：能把“不舒服”说成一个可定位、可修改的问题。
3. **判断结果**：不仅看截图，还能检查真实视频、窗口变化和异常状态。

术语是沟通工具，不是让 AI 做出完美界面的咒语。你的目标是从“帮我美化”进步到“我知道哪里需要改，也能判断改得是否合适”。

## 2. 先掌握这十个词

先理解它们的区别，不必背定义。最后一列是针对本项目的练习说法，不是固定设计规范。

| 中文 / 英文 | 解决什么问题 | 向 AI 表达的例子 |
| --- | --- | --- |
| 信息架构 / Information Architecture | 信息如何分类、组织，功能如何被找到 | “把操作状态、系统消息、连接设置分开组织，不要全部堆在 HUD 上。” |
| 视觉层级 / Visual Hierarchy | 先看什么、后看什么 | “关键告警和本车状态优先，装饰与次要标签弱化。” |
| 视觉权重 / Visual Weight | 哪个元素最吸引注意 | “右侧仪表抢走了视频的注意力，减少装饰面积和亮度。” |
| 亲密性 / Proximity | 相关信息能否被看成一组 | “射速和发弹量靠近，用间距分组，不加大背景框。” |
| 对齐 / Alignment | 信息是否有稳定的排列秩序 | “数据标签沿同一条左边线，数值按同一规则对齐。” |
| 留白 / White Space | 元素之间是否有呼吸空间 | “增加消息行之间的间距；留白可以是可见的视频，不一定是白色背景。” |
| 排版 / Typography | 字体、字号、字重、行高如何协作 | “关键数字、标签、说明分成三级，同一级保持一致。” |
| 对比 / Contrast | 信息能否辨认，类别能否区分 | “在明亮和昏暗的视频背景上，关键文字都必须可读。” |
| 渐进式披露 / Progressive Disclosure | 非必要功能何时出现 | “播放设置默认收起，需要时展开；关键告警仍持续可见。” |
| 设计变量 / Design Tokens | 怎样避免每个地方各用一套样式 | “统一规定文字颜色、字号、间距与线宽，再调整具体组件。” |

信息架构决定“放什么、怎么分类”，视觉层级决定“这些内容谁更突出”。设计变量是可复用的样式值，不代表必须引入新框架。比如约定三档字号、几档间距，就能开始形成自己的视觉规则。

视觉层级、尺度、平衡、对比与格式塔的入门解释，见 [NN/g：5 Principles of Visual Design in UX](https://www.nngroup.com/articles/principles-visual-design/)。字体组织可配合 [Ant Design：字体](https://ant.design/docs/spec/font-cn/) 阅读。这里只学习原则，不迁移到 Ant Design 技术栈。

## 3. 用操作任务组织 HUD，不要用“还有一个功能”组织 HUD

对于图传终端，可以先问四个问题：

- 操作手正在瞄准还是移动？什么信息能帮助当前判断？
- 当前发生了什么异常？用户必须立刻知道什么？
- 哪些内容只是偶尔查看，例如摄像头选择和播放设置？
- 哪些文字只是解释，并不需要和关键数值一样突出？

本项目可以用下面的分类做练习，而不是直接据此修改代码：

| 信息类别 | 例子 | 组织思路 |
| --- | --- | --- |
| 主任务内容 | 实时视频、必要的瞄准辅助 | 保留中央和侧方视野，装饰不要竞争注意力 |
| 异常与安全状态 | 断线、数据过期、控制锁定 | 正常时克制，异常时明确；不能为了漂亮而隐藏风险 |
| 操作相关读数 | 血量、弹量、射速、云台角度 | 按关联性靠近、稳定对齐，单位与标签不抢数值 |
| 次级工具 | 摄像头选择、回放操作、设置 | 按需展开，展开时避免遮住关键区域 |

“去掉大框”不等于“把所有内容变淡”。可以弱化底板、边框和装饰，却仍保留文字的可读性。红蓝阵营也不能只靠颜色表达，增加“我方·红/蓝”的明确文字更容易确认身份。

一个例子：如果你觉得仪表太抢眼，先判断问题来自数字大小、圆弧亮度还是整体面积。不要同时缩小整个 HUD，否则原本正常的文字也可能变得难读。

## 4. 与 AI 沟通：使用六段式设计说明

下面是可以直接填空的练习模板。它不是仓库规则，也不自动授权任何代码修改。

```text
【任务与用户】
这是 Qt 6/QML 图传操作手终端，用户需要一边看视频一边快速判断状态。
本次只优化 ______，不做整套重设计。

【当前问题】
在截图的 ______ 区域，______ 过于突出/拥挤/难读。
它导致用户 ______。请先确认你是否理解这个问题。

【保持不变】
保留现有功能和数据含义，不改通信、控制权限或安全门。
保留 ______ 的位置与操作方式。

【视觉方向与参考】
图 1 是当前界面，作为结构依据。
图 2 只参考它的 ______，不要照搬业务内容和布局。
请具体说明字号层级、间距、对齐、底板和强调色如何调整。

【禁止与约束】
不要新增大面积不透明框，不遮挡准星与重要视频区域。
不要用持续闪烁、复杂动效或模糊特效来掩盖层级问题。
透明底板不能以牺牲关键文字可读性为代价。

【交付与验收】
先列出最重要的三个问题、建议和取舍，等我确认再改代码。
改后在大/小窗口、明/暗视频、断线/过期状态下检查。
说明已验证的内容，未测的性能不要描述为已达标。
```

Figma 官方建议把任务、背景与约束讲清楚，提供示例，并针对局部迭代；参考图还应明确是精确还原还是风格参考。详见 [Create a Figma Make file](https://help.figma.com/hc/en-us/articles/31304485164695-Create-a-Figma-Make-file) 的 **Prompting** 和 **Working with attachments**。这些沟通方法可以借鉴，但不保证其他 AI 工具有同样功能。

### 反馈时，用“位置 → 现象 → 影响 → 修改 → 保留”

不够明确：

> 有点丑，科技感再强一点。

更容易执行：

> 右侧仪表的圆弧比数据更显眼，分散了看视频的注意力。请先降低圆弧的装饰亮度，统一标签对齐，保留关键数值的可读性。不要移动地图，也不要增加背景框。

如果你不确定解决办法，可以只描述现象和影响，让 AI 给出两个有取舍的建议。不要为了使用术语而假装已经知道答案。

## 5. 前人经验应该怎样变成自己的工作方法

有用的不是收藏几十套提示词，而是形成一个短循环：

1. **定义任务**：这次解决什么，不解决什么。
2. **给出依据**：当前截图、使用场景、少量参考图。
3. **先评审**：让 AI 说明问题与取舍，不急着写代码。
4. **局部修改**：一次只解决一组相关问题，便于比较前后结果。
5. **多场景验证**：截图之外，还看真实视频和状态变化。
6. **沉淀规则**：把已经确认有效的字号、间距、色彩语义记录下来，后续复用。

中文入门可读 [Easy-Vibe：参考 UI 设计规范设计页面和按钮](https://datawhalechina.github.io/easy-vibe/zh-cn/stage-2/frontend/multi-product-ui/)，[Easy-Vibe：AI 设计入门](https://datawhalechina.github.io/easy-vibe/zh-cn/stage-2/frontend/ui-design/) 重点是借鉴设计判断和操作层级，而不是只模仿皮肤。

选读论文 [Why Johnny Can't Prompt，CHI 2023，作者提供的英文 PDF](https://people.eecs.berkeley.edu/~bjoern/papers/zamfirescu-johnny-chi2023.pdf) 研究了非专家设计聊天机器人提示词时的困难，包括缺少系统性试验和过度概括。它不是 HUD 美化实验，也使用较早的模型。本文借鉴的是“有意识地比较和验证”的研究启发，而不是把其结果当作今天所有 AI 的能力结论。

## 6. 美观、顺滑、低延迟，是三个不同的目标

| 目标 | 需要观察什么 | 不能据此直接推断什么 |
| --- | --- | --- |
| 美观与可用 | 层级、对齐、可读性、遮挡、状态表达 | 一张好看的截图不能证明交互可靠 |
| 界面顺滑 | 帧时间是否稳定，是否掉帧或阻塞 | UI 动画顺滑不代表图传延迟低 |
| 图传低延迟 | 从采集到屏幕显示的实际链路耗时 | 本机模拟延迟、视频 FPS 不能代替端到端测量 |

以 60 FPS 为例，每帧约有 16.7 ms 的时间预算，但这不是“图传端到端延迟必须为 16.7 ms”。Qt 官方建议避免阻塞界面线程，并先用性能分析工具找瓶颈，见 [Qt 6.11：Performance considerations and suggestions](https://doc.qt.io/qt-6.11/qtquick-performance.html) 的 **Timing Considerations** 与 **Profiling**。

对本项目，先关注真实视频与 HUD 同时运行时是否卡顿；不要让 AI 仅凭减少几行代码或加上“硬件加速”字样就宣称性能提升。

## 7. 三次学习，每次产出一个小结果

### 第一次：给当前截图标注，而不是改代码

读 NN/g 的视觉原则和 Ant Design 的字体部分。选择当前 HUD 的三个区域，分别写出：

- 它属于主信息、辅助信息还是次级工具？
- 是否存在视觉权重、对齐、排版或对比问题？
- 它有没有影响视频视野？

验收：能用普通话解释问题，再补上准确术语，而不是只说“丑”。

### 第二次：写一份设计说明

读 Easy-Vibe 与 Figma 的指定小节。用六段式模板，只针对一个区域写需求，并请 AI 先评审、不改代码。

验收：别人读完后能知道改哪里、为什么改、什么不能动、怎样算改好。

### 第三次：制定验收场景

先读 Qt 性能文档的两个小节，不需要现在掌握全部优化方法。为你的设计列出以下检查项：

- 1600×900 与 1180×680 等常用逻辑窗口尺寸下是否重叠、截断；系统缩放变化后是否仍可读。
- 明亮、昏暗、细节密集的视频背景上，文字能否辨认。
- 摄像头选择与播放工具展开/收起后，布局是否衔接自然。
- 系统与机器人消息同时出现时，是否仍能分辨类别。
- 切换阵营后是否明确显示我方身份；未知、过期数据是否仍如实表达。
- 异常出现后是否容易发现；工具展开是否影响输入安全边界。
- 有真实视频运行时是否卡顿；哪些性能指标尚未测量。

这些是学习验收建议，不是已经通过的应用验收结果。后续若改变实际界面行为，再补相应测试。
