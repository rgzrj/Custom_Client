# 网络通信与本机联调指南

由项目原创通信专题整理。核心知识可离线学习；下列本项目接口是 2026-10-01 的教学快照，不是正式 RM2027 协议，排障必须以实际配置、契约与源码为准。外部依据见 [readings.md](readings.md)。

## 用 CV 类比理解数据流

从“摄像头→图像→算法→显示”过渡到“发送者→传输→接收→解析校验→状态→显示”。不要让用户先背完整网络体系。

裁判 UDP 与本机 MQTT 入口最终进入共同载荷校验和序号过滤；不要同时灌入互不相关的序号流。视频是独立链路，裁判数据新鲜不证明视频可用。

## 容易混淆的词

| 名称 | 含义或边界 |
| --- | --- |
| IP / Port / Endpoint | 主机或接口、通信入口、协议加地址与端口；只说端口不足以定位 |
| Socket / Bind / Listen | 程序的网络接口、指定本地端点、TCP 服务端等候连接 |
| Loopback | 127.0.0.1 表示本机，不能用它连接另一台电脑 |
| Payload / Serialization | 业务载荷与把结构转换为字节；不是网络连接本身 |
| UDP | 有边界的数据报，不保证送达、顺序或去重 |
| TCP | 可靠有序字节流，不保留应用消息边界 |
| MQTT | broker 按 topic 转发发布/订阅消息，载荷格式由应用另定 |
| JSON / Protobuf | 不同的序列化方案；Protobuf 的 schema 不替代传输与业务校验 |
| Freshness | 距最近一次有效数据多久；连上不等于新鲜 |

MQTT 与 Protobuf 不是二选一：可由 TCP 搬运 MQTT 消息，消息内承载 JSON 或 Protobuf。TCP 一次 read 可能是半包或多包，要按协议包头/长度解析，不把 readAll 当作一条完整 JSON。

QoS 0/1/2 是 MQTT 的交付语义，不是机器人动作完成确认；QoS 1 可能重复，QoS 2 不替代业务去重。retained、keepalive、订阅成功和裁判数据新鲜度分别判断。

## 本机接口教学快照

全部默认绑定/发送到 127.0.0.1；端口可改变，不能靠这张表断言当前程序使用什么：

| 协议 / 默认端口 | 内容 | 判断依据 |
| --- | --- | --- |
| UDP / 39001 | 单报文 UTF-8 JSON 裁判载荷 | 版本、类型、范围、序号等通过校验 |
| TCP / 39004 | MQTT 3.1.1、QoS 0、rm27/sim/v1/referee 主题与相同 JSON | 订阅成功并收到有效新载荷 |
| UDP / 39002 | 视频探针字节 | 只证明探针包到达，不证明出帧 |
| UDP / 39003 | 本机 MPEG-TS，每报文最多 7 个 188 字节 TS 包 | Qt 后端产生有效解码帧，不是官方分片适配 |

JSON channel 的示例为 rm27.sim.v1.referee，和 MQTT topic 不是同一个字段。当前本机 MQTT 是测试子集，不是完整生产协议实现；正式 Protobuf 要等官方定义，不能自拟字段冒充官方接入。

## 逐层诊断，用观察支持结论

| 层次 | 先检查什么 | 不能据此推断什么 |
| --- | --- | --- |
| 环境 | 实际 exe/版本/参数、发送进程、地址、协议和端口 | 安装齐全就一定可用 |
| 传输 | 绑定结果、收包数、TCP 状态 | socket 存在就收到正确内容 |
| 消息 | MQTT SUBACK、主题、完整包边界 | 已连接就已订阅或收到业务消息 |
| 数据 | channel、sequence、解析接受/拒绝、新鲜度 | 收到字节就有合法领域数据 |
| 显示与权限 | Controller 状态、属性通知、QML 表现、模式与闸门 | 数据更新就获准下发指令 |

说明“已确认”“待验证假设”“下一项最小检查”，不要把缺日志当成已定位原因。先跟一包数据走到底，再建议更换库、重装环境或修改架构。

当前代码定位示例：项目根下 contracts/模拟接口-v1.md、src/sim/sim_referee_receiver.cpp、src/sim/sim_mqtt_receiver.cpp、src/app/terminal_controller.cpp、qml/Main.qml。在陌生仓库中先找实际对应文件；没有源码时继续用分层方法，不编造函数与状态。

## 视频与恢复的验收边界

分别检查“尚未收到首帧”“已有帧后停止出帧”“恢复”“重新配置/切源”；只测试正常收帧后停止，不能证明启动时无帧也会告警。没有过画面不应声称保留旧帧；保留末帧必须标明非实时。

探针收包、实际 TS 接收、有效解码帧、屏幕显示不混为一谈。0 FPS 说明测量窗口内没出帧，不独自证明是发送端、防火墙或解码器的问题。

600ms 裁判过期、700ms 视频帧超时是当前项目阈值示例，含事件调度误差；不转成普适网络标准。接收后时长优先用单调时钟；未校准的跨机 Unix 时间相减不能证明单向延迟。模拟 latency/loss 字段与实测指标分开报告。

## 环境检查保持只读

本机环回联调不需赛事静态 IP、网关或 DNS；0.0.0.0 是常见服务绑定范围，不是发送目的地址。改成它可能扩大网络暴露，不作为随意排障动作。

以下只是可选的本机观察命令，运行前核对实际端口；它们不发送测试载荷：

```powershell
Get-NetUDPEndpoint | Where-Object { $_.LocalPort -in 39001,39002,39003 } |
    Select-Object LocalAddress,LocalPort,OwningProcess
Get-NetTCPConnection | Where-Object {
    $_.LocalPort -eq 39004 -or $_.RemotePort -eq 39004
} | Select-Object LocalAddress,LocalPort,RemoteAddress,RemotePort,State,OwningProcess
```

无匹配输出、UDP 没有 Established 状态都不能单独证明故障。观察 PID 不等于有权结束该进程。ping 不证明业务端口可用；Test-NetConnection -Port 测 TCP 而非 UDP，且会主动连接，不归类为纯观察。

不自动改网卡、防火墙、系统 PATH，不关闭未知进程或扫描外部网络。即使用户要求实施本机联调，也先核对目标与隔离端口；模拟和回放保持真实控制禁用。

## 向 AI 描述问题

```text
【范围】本机模拟，不连接官方网络，不发送真实控制。
【链路】谁发送、谁接收？UDP/TCP/MQTT？视频还是裁判数据？
【端点与格式】实际地址、端口、topic、channel、载荷版本。
【现象】上次正常操作、现在的操作、运行入口和错误原文。
【依据】契约、脱敏样例、日志、截图；哪些层已有证据？
【要求】先判断故障在哪层，不猜官方字段，不擅自改网络环境。
【验收】恢复正常、异常独立、旧数据不当实时、控制保持锁定。
```

练习可按三次安排：画两条裁判入口并解释分层；用已有模拟器独立停/恢复裁判与视频并观察；从固定样例推导错误版本、类型、长度、序号及漂移的拒绝行为。仅讨论练习不等于授权运行、发包或修改契约。
